# 地理编码 TODO

这份文档用于记录 `Monid -> Strale /x402/address-geocode` 接入后的当前结论、问题清单和后续推进计划。

## 当前状态

- 已完成 `Monid` 地理编码 provider 接入，当前会作为 `AMap` 之后、公共 geocoder 之前的新增 fallback。
- `MONID_API_KEY` 已支持通过 `.env` 启用。
- 已完成基础单元测试，验证了：
  - `Monid` 请求 payload 正确
  - `Monid` 在 geocode 链路中的触发顺序正确
  - 启动检查可识别 `MONID_API_KEY`

## 已验证结论

### 国内地点

- 明确地标和明确地址整体表现较好。
- 例如：
  - `北京市东城区天安门广场`
  - `上海市黄浦区外滩`
  - `西安市雁塔区大雁塔`
- 这类地点解析结果基本可直接使用。

### 国外地点

- 英文地址或足够明确的目标，解析精度较高。
- 例如：
  - `Paris, France`
  - `Colosseum, Rome, Italy`
  - `Statue of Liberty, New York`
- 中文国外地名存在明显歧义风险。
- 例如：
  - `法国巴黎` 可能错误命中到中文同名地点
  - `意大利罗马斗兽场` 可能错误命中到国内同名地点

## 当前主要问题

1. 国外中文地名容易歧义，尤其是“国家 + 城市”或“国家 + 景点”的写法。
2. 当前 geocode 成功后不会额外做结果质量重排，命中错误目标时缺少自动纠偏。
3. 现有链路没有把“可能命中错误但返回成功”的结果单独标注出来。
4. 对国外中文地点缺少统一的 query 归一化策略。

## 后续计划

### P1. 做国外中文地名纠偏

- 为常见的“国家 + 城市 / 景点”写法增加轻量归一化。
- 优先尝试把中文国外地名转换成更稳定的英文查询词。
- 示例方向：
  - `法国巴黎` -> `Paris, France`
  - `意大利罗马斗兽场` -> `Colosseum, Rome, Italy`
  - `法国巴黎埃菲尔铁塔` -> `Eiffel Tower, Paris, France`

### P2. 增加结果质量校验

- 对 geocode 返回结果增加简单的可信度检查。
- 重点校验：
  - 返回地址中是否包含预期国家 / 城市
  - 中文 query 是否被解析到明显错误国家或城市
  - 对景点类 query，返回 `place_type` 是否合理

### P3. 引入低置信结果待审机制

- 对“请求成功但疑似命错目标”的结果做标记。
- 可选方案：
  - 写入 `hard_place_review_queue`
  - 记录到 geocode review 报表
  - 为后续人工校正保留 query / result / display_name / provider 信息

### P4. 扩展测试样例

- 增加更系统的国内 / 国外地理编码样例集。
- 覆盖场景：
  - 国内明确地址
  - 国内模糊地点
  - 国外中文城市
  - 国外中文景点
  - 国外英文城市
  - 国外英文景点

### P5. 评估 provider 路由策略

- 评估是否应对“国外中文地名”优先走 `Monid` 或优先走改写后的英文 query。
- 对国内地点继续保持 `AMap` 优先。
- 必要时为国内 / 国外 / 歧义地点拆分不同策略。

## 建议执行顺序

1. 先做 `P1` 国外中文地名纠偏。
2. 再做 `P2` 结果质量校验。
3. 然后接 `P3` 低置信待审机制。
4. 最后补 `P4` 样例测试和 `P5` provider 路由优化。

## 完成标准

- 国外中文常见地点的误匹配率明显下降。
- 出现明显错配时，可以自动识别或进入待审队列。
- 有一组可复用的真实样例测试，能持续回归验证精度变化。
